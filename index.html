A UI engine built for C++ developers.

Framm is designed specifically for developers who demand both control and efficiency when building native software interfaces. It is not positioned as just another UI toolkit or experimental library, but rather as a carefully engineered foundation for professional-grade applications where responsiveness, clarity, and maintainability are essential.

The purpose of Framm is to simplify the process of building modern user interfaces without sacrificing performance or introducing unnecessary complexity. It is a system that aims to provide the best parts of immediate-mode tooling and structured UI frameworks, while avoiding the weaknesses of both. Every design decision is made with the goal of improving developer workflow and reducing friction.

01 Problem

What is broken today?

UI development is fragmented between fast but shallow tools and powerful but heavy frameworks.

Many existing UI solutions fall into two categories: immediate-mode libraries that are simple, fast, and easy to integrate, and comprehensive frameworks that include full-featured layout systems and styling engines. Immediate-mode tools are beloved for their ability to render interfaces quickly and support rapid iteration, but they often lack the structural depth required for large-scale applications.

Developers frequently find themselves layering additional abstractions just to achieve consistent spacing, reusable layouts, or predictable interface behavior. These compensations accumulate into technical debt that undermines the very simplicity that made the tool appealing in the first place.

On the other side, comprehensive frameworks deliver a lot of capability, but they also introduce significant overhead in complexity, build size, and architectural constraints. These frameworks can become rigid, verbose, and difficult to optimize, which undermines the responsiveness that many native tools require.

The net effect is a fragmented ecosystem where developers are forced to choose between speed and structure, simplicity and capability. There is no middle path that honors both without compromise. Framm exists to fill that gap.

02 Approach

How Framm solves it

Combining immediacy with structure to deliver a better foundation for native software.

Framm is designed to address the gap between lightweight UI libraries and heavyweight frameworks. It provides an interface that feels immediate and intuitive, while maintaining a structured layout and rendering system underneath. This hybrid approach allows developers to write clean, concise code without losing the ability to build complex, adaptive interfaces that scale with the application.

The engine is not intended to replicate existing tools. Instead, it aims to redefine the balance between usability and capability by offering a consistent, developer-friendly surface on top of a carefully engineered architecture.

Framm is built to make modern UI development feel natural, while also preserving the performance and transparency required for professional native software. The goal is not to abstract away complexity but to provide the right primitives so complexity never becomes overwhelming.

01

Immediate-mode surface

Developers interact with Framm through an API that feels direct and low-ceremony, enabling rapid prototyping and tight iteration loops without boilerplate.

02

Structured internal layout

Beneath the surface, a full layout engine handles measurement, constraint resolution, and adaptive sizing — giving you the power of a full framework without its verbosity.

03

Optimized render pipeline

A batched, GPU-aware renderer processes all UI elements as a unified scene, minimizing draw calls and maximizing frame rate stability across complex layouts.

04

Modular, composable design

Every subsystem is independently evolvable. Adopt only what you need, extend what you want, and build plugins without touching the core runtime.

03 Performance

Built for speed

Every part of Framm is engineered with efficiency as a first-class concern.

Framm's foundation is rooted in modern C++ practices that emphasize memory control, minimal overhead, and consistent frame rates. The engine is designed to minimize allocations, reduce unnecessary work, and keep render pipelines efficient. Developers can focus on building interfaces without needing to make low-level performance trade-offs in their application code.

Rendering is handled through an optimized pipeline that focuses on batching and minimizing draw calls. By treating UI elements as part of a cohesive scene rather than isolated components, Framm maximizes GPU efficiency and avoids the common bottlenecks that slow down complex layouts.

Memory management follows a pool-based allocation strategy designed for predictable performance. Rather than relying on general-purpose heap allocations that can fragment over time, Framm uses dedicated pools for UI nodes, layout data, and render primitives. This keeps cache locality high and allocation overhead minimal, even in interfaces that update every frame.

⬡

Memory pools

Pool-based allocators keep heap fragmentation low and cache efficiency high. UI nodes, primitives, and layout data live in dedicated, reusable memory regions.

◎

Batch renderer

UI elements are collected into batches by material and depth before submission to the GPU. This eliminates redundant state changes and maximizes fill rate utilization.

◈

Dirty tracking

Only changed regions of the scene graph are re-evaluated. Static sub-trees are cached and skipped during both layout and render passes, saving significant CPU time.

▲

Zero-cost layout

The layout engine operates in a single forward pass for most cases. Complex constraint graphs are resolved incrementally, never blocking the render thread.

Framm is organized into four distinct layers, each with a clearly defined responsibility. This separation ensures that changes to one layer do not cascade unpredictably into others, making the engine easier to reason about, test, and extend over time.

The application layer is where your code lives. It communicates with Framm exclusively through the public API, which provides layout, styling, event handling, and component management. This layer is intentionally decoupled from internal details, so your code remains stable as the engine evolves.

The runtime core manages the scene graph, memory allocation, and change detection. It is the most performance-critical part of the system. The render backend sits below the core and is deliberately swappable — enabling support for different graphics APIs or custom rendering pipelines without touching anything above.

Separation of concerns

Each subsystem owns its domain. No layer reaches across its boundary into another's internals.

Swappable backends

The rendering layer is an abstraction. Future backends for Vulkan, Metal, or WebGPU can be added without rewriting layout or style logic.

Incremental adoption

You can use the layout engine without the style system, or the style system without the component API. Take what you need.

05 Layout

Layout and styling

Structured layout with a lightweight, expressive styling system.

Framm introduces a layout system that remains intuitive while providing greater flexibility than simple stacking models. The system is designed to adapt cleanly to changing content and screen sizes, enabling developers to build interfaces that feel stable and predictable without manual positioning or constant recalculation.

Styling is handled through a consistent, minimal system that supports color schemes, spacing, typography, and component-level customization. It avoids the excess of larger theme engines by offering just enough structure to achieve polished visuals while staying lightweight and easy to reason about.

The layout engine performs a single-pass measurement and placement cycle for most interface configurations. Complex adaptive layouts use a constraint-resolution step that is isolated from the frame render, ensuring that even deeply nested structures do not introduce frame time spikes.

08 Code

Code preview

Framm is expressive, concise, and easy to reason about.

The examples below demonstrate how native UIs can be declared with a clean, composable API that stays readable even as interfaces grow in complexity. Framm code reads like a layout description, not a sequence of imperative commands. 

#include <framm/core.h>

using namespace framm;

int main() {
  auto app = Application::Create("Studio");
  auto window = app.CreateWindow({"Framm", 1280, 780});

  window->Layout(
    Column()
      .Spacing(16)
      .Add(Text("Dashboard"))
      .Add(Row()
        .Add(Button("Build"))
        .Add(Button("Inspect")))
  );

  return app.Run();
}
#include <framm/core.h>
#include <framm/widgets.h>

using namespace framm;

auto BuildDashboard() {
  return
    Column()
      .Fill()
      .Spacing(0)
      .Add(Topbar()
        .Add(Label("Framm Studio").Bold())
        .Add(Spacer())
        .Add(Badge("v0.4.2")))
      .Add(Row()
        .Fill()
        .Add(Sidebar()
          .Width(240)
          .Add(NavItem("Inspector"))
          .Add(NavItem("Scene"))
          .Add(NavItem("Settings")))
        .Add(ContentArea()
          .Padding(24)
          .Add(MetricGrid()
            .Add(MetricCard("Latency", "1.9ms"))
            .Add(MetricCard("Stability", "99.8%"))
            .Add(MetricCard("Footprint", "4.1MB")))));
}

int main() {
  auto app = Application::Create("Studio");
  auto window = app.CreateWindow({"Dashboard", 1440, 900});
  window->Layout(BuildDashboard());
  return app.Run();
}
#include <framm/style.h>

using namespace framm;

auto theme = StyleSheet{
  .colors = {
    .background = Color::Hex("#0d0d0d"),
    .surface    = Color::Hex("#161616"),
    .accent     = Color::Hex("#c8ff00"),
    .text       = Color::Hex("#e8e8e8"),
    .muted      = Color::Hex("#555"),
  },
  .spacing = SpacingScale::Custom({ 4, 8, 12, 16, 24, 32, 48 }),
  .radius  = 6.0f,
  .font    = Font::Load("JetBrainsMono", 14),
};

int main() {
  auto app = Application::Create("Styled App");
  app.SetStyleSheet(theme);
  auto w = app.CreateWindow({"Framm", 1280, 780});
  w->Layout(Column().Add(Text("Styled interface")));
  return app.Run();
}
#include <framm/core.h>
#include <framm/events.h>

using namespace framm;

int main() {
  auto app = Application::Create("Events Demo");
  auto w   = app.CreateWindow({"Framm", 1280, 780});

  int count = 0;

  w->Layout(
    Column()
      .Spacing(16)
      .Add(
        Button("Click me")
          .OnClick([&]() {
            count++;
            return UpdateState([&](Layout& l) {
              l.Find("counter").SetText(
                "Count: " + std::to_string(count));
            });
          }))
      .Add(Text("Count: 0").Id("counter"))
  );

  return app.Run();
}

11 Philosophy

Philosophy

A deliberate engine for real software work.

Framm is guided by the belief that software tools should empower developers rather than constrain them. The engine is built around a clear set of principles: flexibility without losing structure, performance without sacrificing readability, and extensibility without adding unnecessary complexity.

Every design decision within Framm is made with the goal of improving the developer's workflow and reducing friction during development. The engine does not try to do everything. Instead, it tries to do the right things exceptionally well, and provide clean seams where you can take over.

The long-term vision is to become a reliable and widely adopted foundation for both small and large native projects. That means prioritizing stability, consistency, and continuous improvement, while staying responsive to real-world developer needs and avoiding the accumulation of legacy complexity.

I
Clarity first

Clear APIs and predictable layout behavior reduce cognitive load and improve maintainability. Surprise is a failure mode, not a feature.

II
Performance always

Optimized rendering and disciplined memory usage keep interfaces smooth under load. Performance is not an afterthought — it is the foundation.

III
Engineered for growth

A modular architecture makes it easier to extend Framm without disrupting the core system. New capability should not cost existing stability.

IV
Developer respect

Framm assumes competence. It provides primitives and honest abstractions rather than opinionated magic that hides the system from you.

Active development

Framm is being built for developers who demand the best from their tools.
